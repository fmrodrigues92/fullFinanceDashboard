## Achados

### [SEC-01] Comando gera recibo com `valor` bruto para configs percentuais · MÉDIO

**Arquivo:** `app/Console/Commands/GenerateProlaboreRecordsCommand.php` linha 92

**Problema:** ao criar o recibo automático, o comando usa `$config->valor` diretamente. Para configs com `tipo = 'percentual'`, `$config->valor` armazena o percentual (ex.: `28.00`), não o valor em BRL. O registro gravado em `prolabore_records` terá `valor = 28.00` em vez de, por exemplo, `R$ 4.200,00`. Como `GetProlaboreDashboardUseCase::classify()` dá precedência a registros sobre configs para meses passados, o dashboard exibirá o valor errado indefinidamente para esses meses.

**Correção recomendada:**

```php
// Antes de criar o registro, calcular o BRL para configs percentuais.
// É preciso buscar o faturamento real da competência para a empresa.
// Sugestão de implementação no handle():

$faturamento = InvoiceModel::query()
    ->where('company_id', $companyId)
    ->where('is_simulation', false)
    ->whereNull('deleted_at')
    ->where('data_emissao', '>=', $competencia->format('Y-m-d'))
    ->where('data_emissao', '<', $competencia->modify('+1 month')->format('Y-m-d'))
    ->sum(DB::raw('valor_brl::numeric'));

// E ao criar o ProlaboreRecord:
$valorBrl = $config->tipo === 'percentual'
    ? round((float) $faturamento * ($config->valor / 100.0), 2)
    : $config->valor;

$record = ProlaboreRecord::create(
    // ...
    valor: $valorBrl,
    // ...
);
```

> Alternativa mais limpa: injetar `InvoiceRepository` no comando e usar o método já existente
> `faturamentoPorCompetencias()` para obter o total real do mês anterior.

### [SEC-02] Exceção não capturada na transação pode silenciar falhas e interromper o loop · BAIXO

**Arquivo:** `app/Console/Commands/GenerateProlaboreRecordsCommand.php` linhas 82–93

**Problema:** a verificação `existsForPartnerAndCompetencia` ocorre fora do `DB::transaction`. Em execução concorrente (improvável, mas possível se o scheduler Laravel não travar corretamente), dois processos passam a verificação e um deles falha no insert com violação do unique constraint em `prolabore_records`. A exceção não capturada encerra o `foreach` de sócios e pode interromper o processamento de empresas subsequentes na mesma execução — outras empresas naquele mês não receberiam o recibo automático.

**Correção recomendada:**

```php
try {
    DB::transaction(function () use ($companyId, $config, $userId, $competencia, $valorBrl): void {
        $record = ProlaboreRecord::create(
            companyId: $companyId,
            partnerId: $config->partnerId,
            userId: $userId,
            competencia: $competencia,
            valor: $valorBrl,
            observacao: null,
            origem: 'automatico',
        );
        $this->recordRepo->save($record);
    });
    $created++;
} catch (\Throwable $e) {
    // unique violation por race condition — registrar e continuar
    $this->warn("Recibo já existia (race): company={$companyId} partner={$config->partnerId}");
    $skipped++;
}
```

## Checklist completo (sem achados adicionais)

**Isolamento multi-tenant:** correto. `DashboardController` deriva `$companyIds` exclusivamente de `ListCompaniesUseCase($userId)`, que filtra por `user_id` na tabela `companies`. Todas as queries de dashboard (`faturamentoPorCompetenciasMultiEmpresa`, `faturamentoSummaryForCompanies`, `dashboardRecordsForCompanies`, `configsWithPartnerNamesForCompanies`) filtram por `whereIn('company_id', $companyIds)`, sem possibilidade de injeção de IDs externos.

**Autorização em ProlaboreConfigController:** `store` chama `$this->authorize('update', $company)`; `update` e `destroy` executam `abort_if(config->company_id !== company->id, 404)` seguido de `$this->authorize('update'/'delete', $config)`. Tripla verificação: middleware auth + Policy + ownership check explícito.

**Validação de inputs:** `StoreProlaboreConfigRequest` e `UpdateProlaboreConfigRequest` cobrem `tipo` (in:fixo,percentual), `valor` (numeric, gt:0, e max:100 para percentual). Nenhum input de usuário chega raw aos use cases.

**SQL Injection em `selectRaw`/`groupByRaw`:** todas as expressões raw são literais SQL sem interpolação de variáveis de usuário. Parâmetros chegam via bindings do Eloquent (`whereIn`, `where`, `whereNull`).

**Mass assignment:** `EloquentProlaboreConfigRepository::save()` constrói `$data` explicitamente a partir do domain object — nenhuma atribuição direta de `$request->all()`.

**PII em responses:** `presentPartner()` expõe CPF e nome do sócio somente para o usuário autenticado dono da empresa. CPF não aparece em logs.

**Performance — índices:** `prolabore_records` ganhou `index(['company_id', 'competencia'])` na migration `000001`; `prolabore_configs` tem FK + unique em `(company_id, partner_id)`. As queries de dashboard usam `company_id` indexado. Sem N+1 detectado — todas as queries são agregações batch via `whereIn`.

**Configuração e debug:** sem `dd()`, `dump()`, `var_dump()`, `console.log()` ou credenciais hardcoded nos arquivos auditados.
